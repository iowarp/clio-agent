CLIO gives the agent new abilities in two forms:

- A **connector** is an MCP server packaged for CLIO: a molecule viewer, a PDF viewer,
  a NASA data search. It has a logo, it says what it needs from you, such as an address
  or a sign-in, and it lists its tools. Many connectors also show their results as a
  live [app](/docs/apps/).
- A **plugin** brings skills: instructions for doing a kind of work well. It may also
  bring an MCP server. The ParaView plugin, for example, brings a skill for working
  with ParaView and the server that drives it; the Home Assistant plugin brings two
  skills and the ha-mcp server.

Extensions shows each as what it is. A connector's row reads **Connector** and
**1 MCP server (4 tools)**; a plugin's row reads **Plugin** and what it brings, such as
**2 skills, 1 MCP server (27 tools)**. A plugin that brings a server is listed once, as
the plugin.

You add both to a conversation the same way, and the agent can offer either one when a
request needs it. Adding one changes only that conversation, so a conversation that
does not use ParaView never carries ParaView's tools.

In a conversation that has already started, adding or removing a connector or plugin
asks how the change reaches the agent, as described in
[Agents and plugins](/docs/agents-and-plugins/#how-a-change-reaches-the-agent). The
conversation's plugin list then shows the connector as **Connector you added**; remove
it there to take it out of this conversation.

To have a connector or plugin in every new conversation of an agent, add it to that
agent: open the agent in **Settings → Agents**, or save a conversation's setup as an
agent.

## When the agent offers a connector or plugin

The agent knows which connectors and plugins this conversation does not have: each by
name, with a line about what it does and, for a plugin, the marketplace it comes from.
When your request needs one, it asks with a card instead of guessing or working around
it. The card has four rows:

1. The logo and **Add Geo to this conversation?**, with its state at the right:
   **Enabled**, **Not enabled (Add turns it on)**, or **Plugin from** its marketplace.
2. What it is, in one line.
3. **Why**: the agent's reason, on one line. Select it to read all of it.
4. **Add**, **Not now**, what Add brings (for example **1 MCP server (12 tools)** or
   **2 skills and 1 MCP server (27 tools)**), and **View connector** or **View
   plugin**, which shows what it brings without answering the card. A connector with
   optional settings also shows **Settings** with their number.

Rows it requires, such as an address or a token, appear on the card above the buttons,
filled in when you have already given them.

Choose **Add** and the connector or plugin joins this conversation only, enabled first
if it was off, and the agent continues your request in the same reply, with the new
tools and skills. Choose **Not now** and nothing changes. The agent never adds
anything by itself, and it does not offer what a request has no use for.

## Add your own MCP server

For a service that is not in the catalog, choose **Add → Add by URL or command** in
Extensions. Give it a name, then either the address of a remote MCP server (**URL**) or
a command that starts one on the machine running CLIO (**Command**), with its
arguments as a JSON list.

<Capture client:visible image={await captureImage(addByCommand)}
  alt="The Add by URL or command dialog over Extensions, set to Command: name hdf5, command clio-kit, arguments mcp-server and hdf5, with Advanced folded and an Add button"
  caption="A local MCP server added by command. Here, clio-kit's HDF5 server."
/>

CLIO adds it as a connector with a monogram, and you add it to conversations like any
other. Its card shows the address, and a **Sign in** row when the service asks for one.
**Remove** deletes a connector you added this way. Anything under **Advanced**, such as
request headers, an authentication mode or environment variables, makes it a plain MCP
connection instead; see [Connect tools and services](/docs/mcp-servers/).

Discover also lists servers from the public MCP Registry, each with **Install**, which
fills in the same form.

## Where plugins come from: marketplaces

Plugins come from marketplaces. The `clio` marketplace ships with CLIO and is trusted
when it is installed. You can add others, such as a lab's own marketplace or IOWarp's
`clio-kit`, under **Extensions → Marketplaces**, then trust them before their plugins
can run. The agent can offer the plugins of every marketplace you add, the most
recently added first.

## State in words

A connector's or plugin's state reads the same everywhere it appears:

| State | Meaning |
|---|---|
| **Ready** (on a card, **Ready, 4 tools**) | It answered and its tools are available. In a list, the tool count is in what it brings: **1 MCP server (4 tools)**. |
| **Needs** followed by what, such as **Needs a sign-in** | A required row is empty. Optional rows never hold a connector back. |
| **Can’t be reached** | CLIO started or called it and it did not answer. The card gives the reason, for example that nothing answered at the address. |
| **Not enabled** | It is turned off. |
| **In this conversation** | Shown in a conversation's **Add plugin** menu for one it already has. |

**Turn off** stops it. A conversation you added it to keeps it in its list but cannot
use it, and says it left because the connector is turned off; enable the connector
again and it is back in that conversation. Its values and secrets are kept, so
enabling it again needs nothing more.

## The setup card

Each row of a connector's card is one thing the connector needs:

- **Address** or **value**: a text field, or a list to pick from. Some rows say
  **The agent can set this**.
- **Secret**: a masked field, for a token or a key. After you save it, the field
  stays empty and says **Saved. Type a new one to replace it**. Leaving it empty
  keeps the saved secret.
- **Sign-in**: a **Sign in** button that opens the service's own sign-in page. The
  row then reads **Signed in** or **Not signed in**.

Rows marked **Required** must be filled before the connector is ready. When you change
a value, CLIO reconnects to the service, or restarts it if it runs on your machine, and
lists its tools again.

### Values for one conversation, and defaults

The values in Extensions are your **defaults**: every conversation uses them unless it
has its own. A value given inside a conversation, by you on a card or by the agent, is
that **conversation's own**. Pointing ParaView at node08 in one conversation leaves
another conversation's ParaView on this machine, and the views in both stay open.

On a card in a conversation, each address or value row has **Save as default**. Leave
it clear to keep the value in this conversation only; the row then reads **This
conversation only** and shows the default it replaces. Tick it to make the value your
default for new conversations too. Secrets and sign-ins are always yours for every
conversation.

A conversation with values of its own gets its own copy of the server, so it never
changes what another conversation is connected to. Reopening a view in a conversation
uses that conversation's values.

A secret goes to the service only. It is kept in CLIO's credential file in your
configuration folder, readable only by you, and never appears in the conversation, in
what the model reads, or in the logs.

### When a call needs something first

If the agent calls a tool of a connector that still needs something, the call waits and
a setup card appears in the conversation. It names the tool that is waiting and shows
only the missing rows.

- Fill them in, or sign in, and choose **Continue**. The same call then runs and
  returns its result. You do not need to ask again. A card that needs only a sign-in
  continues by itself once you have signed in.
- Choose **Decline**, or press Esc, to refuse. The call returns a refusal that names
  the connector, and the agent tells you it could not use it.
- Stopping the reply also ends the waiting call.

The same card appears when a service stops accepting a sign-in it accepted before.

## What the agent can change, and what asks first

Some values are things you might say in passing: "the ParaView I want is on node08". A
row marked **The agent can set this** can be changed by the agent with its
`set_connector_value` tool, several values in one call. It sets them for the
conversation it is in, never as your defaults. The agent can never set a secret or sign
in for you, change a row that is not marked, or turn a connector on or off.

Calls to a connector's tools, to an app's own tools and to `set_connector_value` follow
the conversation's [permissions](/docs/permissions/). Under **Ask first** each one asks,
with **Allow once**, **This session** and **This workspace**; under **Bypass checks**
none asks. The offer card itself is the question for adding a connector or plugin.

## Connectors CLIO includes

None is enabled until you enable it. Each runs on the machine that runs CLIO, except
Burette, which is a hosted service. The catalog's plugins are listed after them.

### Geo

Shows stations, regions, footprints and tracks from GeoJSON on an interactive 3D globe,
makes map images, finds places by name, and queries public map layers. It runs IOWarp's
Geo server through the `clio-kit` launcher and needs nothing from you. Click a feature
on the globe and the agent is told which one; in a dashboard, the globe's selection can
be linked to a table both ways. See the [Apps walk-through](/docs/apps/).

The globe needs the Geo server 2.4.0 or later, which comes with the `clio-kit` release
that carries it. The globe is drawn with CesiumJS, loaded from cesium.com, over
OpenStreetMap tiles.

### 3D globe

Runs the [MCP Apps map example server](https://github.com/modelcontextprotocol/ext-apps/tree/main/examples/map-server)
(`@modelcontextprotocol/server-map` 2.0.4) through `npx`, and frames a named region on
a 3D globe. It needs Node.js 20 or later. It does not draw points, outlines or GeoJSON,
and it does not zoom closer than about 500 km above the ground; use Geo for those.

### PDF viewer

Runs the [MCP Apps PDF example server](https://github.com/modelcontextprotocol/ext-apps/tree/main/examples/pdf-server)
(`@modelcontextprotocol/server-pdf` 2.0.4) through `npx`, and shows a paper in a viewer
you can page through, search and zoom, in the conversation, in a tab or in a dashboard.
It needs Node.js 20 or later. It opens papers by address from arXiv, bioRxiv, medRxiv,
ChemRxiv, Zenodo, OSF, HAL and similar archives. Ask, for example, "Show me arXiv
2611.15421 so I can read it". The agent reads the page you are on, can jump to a
section, search the paper and take a picture of a page. It cannot open a file from your
workspace yet.

### NASA Earthdata

Runs [earthdata-mcp-server](https://github.com/datalayer/earthdata-mcp-server) 0.6.0
through `uvx` (about 250 MB on first use). It searches NASA's Earthdata catalog for
Earth-science datasets and their files. Searching needs no account. To download files,
enter your free [NASA Earthdata Login](https://urs.earthdata.nasa.gov) username and
password in its two optional rows; the password is kept as a secret.

  caption="A granule search with NASA Earthdata. Without an Earthdata Login the download failed, and the agent said so."

### Burette

[Burette](https://github.com/SergeiNikolenko/Burette) shows molecular structures from
the Protein Data Bank in Mol*, and draws or edits molecules in Ketcher. It is a hosted
service and needs nothing from you. Ask, for example, "Show PDB 1CRN". Its viewer draws
nothing in a frame 600 pixels wide or narrower; open it in a tab and widen the panel.

### SPICE circuit simulation

Runs [ltspice-mcp](https://github.com/cognitohazard/ltspice-mcp) 0.8.0 through `uvx`,
and plots waveforms in the conversation. Install ngspice, or LTspice on Windows, first.
It does not support macOS.

## Plugins CLIO includes

These plugins bring skills together with an MCP server, and are enabled the same way.
None is enabled until you enable it.

### Home Assistant

Reads sensors and their history from your [Home Assistant](https://www.home-assistant.io),
controls devices, and writes automations, scripts, scenes and dashboards: a lab's or a
greenhouse's monitors as much as a home's. It runs ha-mcp 9.2.0 through `uvx` and offers
27 of its tools. Its two skills are `home-assistant-sensors`, for finding entities and
reading state and history, and `home-assistant-best-practices`, taken unchanged from the
homeassistant-ai skills project, for writing configuration the native way. Both rows are
required:

| Row | What to enter |
| --- | --- |
| **Your Home Assistant address** | The address you open Home Assistant at, for example `http://homeassistant.local:8123`. |
| **Long-lived access token** | In Home Assistant, open your profile, then **Security**, and create one. Kept as a secret. |

ha-mcp starts and lists its tools even when the address or token is wrong, so the card
can read **Ready** until the first call fails; the agent then says that Home Assistant
did not answer. Its tools can change your Home Assistant, such as switching a device or
saving an automation; those calls follow your [permissions](/docs/permissions/), and you
can ask the agent to show a change without saving it.

### ParaView

Brings a skill for working with scenes and the server that opens your data in ParaView
and shows it in a live view in a tab. It needs ParaView 6.0 or later where ParaView
runs. Its server has three settings, all optional, and the agent can set each:

| Row | What to enter |
|---|---|
| **Where ParaView runs** | Empty for this machine. Otherwise an SSH host name, including an alias from your `~/.ssh/config`. |
| **Jump host** | A host to go through, when your SSH configuration does not already give one. |
| **Command to run first** | A line that puts `pvpython` on the path, for example `module load paraview`. |

On this machine, CLIO looks for `pvpython` after running the first command. If there is
none, the first scene request says so and tells the agent how to point ParaView at
another machine.

#### ParaView on another machine

Two hops such as `ssh login` then `ssh node08` are one setting: **Where ParaView runs**
`node08`, **Jump host** `login`. You can also just tell the agent: "Connect to the
ParaView on node08, through login. It needs `module load paraview` first."

- CLIO uses your own `ssh`, keys, agent and `~/.ssh/config`, over one connection.
  Nothing listens on the network on either side.
- The first time on a machine takes a minute or two. CLIO prepares a folder,
  `~/.clio/paraview/<version>/`, with what the view needs. If that machine cannot
  reach the Python package index, it builds the folder from the jump host, which
  shares your home folder on most clusters. Later connections reuse it and take
  seconds.
- If a ParaView server (`pvserver`) is already running on that machine on port 11111,
  the view joins it and shows that session's data.
- File paths are paths on the machine where ParaView runs.
- If the connection drops, the scene is kept there and the next request reconnects.
  With no connection for 30 minutes, ParaView on that machine saves the scene and
  stops.

<Aside type="caution" title="Key-based SSH only">
A host that asks for a password or a one-time code on every connection does not work.
The first request fails at once with a message that interactive sign-in is needed.
Use an SSH key or agent that the host accepts.
</Aside>
