# v0.10 Program — MCP v2, Federation, and the Session v3 UI

**Status:** ACTIVE, 2026-07-30. All owner decisions closed (D1 multi-connection client,
D2 shared schema package, D3 Codex workhorse via codex-plugin-cc). This doc is the live
program plan and is updated as slices land.
**Repos:** iowarp/clio-agent + iowarp/gact-tui (+ relay-side asks filed on iowarp/clio-relay).
**Render target:** the owner's Clio Session v3 prototype (authoritative; full inventory captured
2026-07-29). **Protocol target:** MCP 2026-07-28 ("MCP v2") + extensions
`io.modelcontextprotocol/tasks` (SEP-2663) and `io.modelcontextprotocol/ui` (SEP-1865).

## 0. The one-sentence thesis

One spawn primitive, one task record, one artifact record, two transports (local, relay),
one part grammar on the wire, one component kit in the client — MCP v2 semantics end to end,
rendered by the Session v3 UI.

## 1. Program structure decision

**ONE program umbrella, five phase subtrees, strictly gated phase boundaries.**

- One parent issue in clio-agent (`v0.10 program`) whose children are five phase parents;
  each phase parent owns an ordered slice tree. gact-tui gets one mirrored umbrella whose
  children are the client slices of P3/P4/P5 (same numbering, cross-linked).
- Rationale: the pillars share three schema decisions (task record, artifact record, part
  grammar) — separate campaigns would re-litigate them (the unified-design rule). But phases
  are real sequencing boundaries with their own gates, so the tree gives per-phase workflows
  without splitting design authority.
- Version semantics: P0–P2 ship as 0.10.0-alpha tags off develop as they gate; v0.10.0 cuts
  after P5. Nothing merges to main until the program's composed gate is green.

## 2. Owner decisions baked in (from 2026-07-29 review)

1. Documents and Live Web are IN scope (Monday meeting feature ask; "full web semantic" for
   sharable interactive reports). Office rendering = model-rendered floor; builder/LibreOffice
   is a designed-for extension, not built now. Email integration = future pillar, seams only.
2. Sampling pillar dead (deprecated in MCP v2); its use case (visual elements requesting model
   output) rides the MCP Apps bridge + MRTR/task input rounds.
3. No hardcoding prototype semantics one-by-one; general capabilities instead
   (message-an-agent covers steer/queue/wake; placement covers local/remote spawn).
4. UI is a unification point: component kit first, every surface is composition; a
   kit-conformance check guards it.
5. One spawn primitive — `relay_submit_agent`-style split tools are deletion targets.
6. MCP v2 compliance is a program goal in itself (research directions ride the task system).

**Open owner decisions this doc forces (full context so they are decidable):**

- **D1 — multi-backend topology (DECIDED 2026-07-30, owner correction).** Primary agents
  and subagents are DIFFERENT things and use different transports:
  - **Primary agents** = full gact backends on reachable endpoints. gact-tui becomes a
    MULTI-CONNECTION client: today's single connection (base URL + SSE + cursor state)
    becomes a first-class connection object and the UI holds several. Tunnels are
    USER-PROVIDED (ssh -L port-forward, LAN, VPN) — the app never proxies or federates
    gact-to-gact; there is NO hub module. Every session is homed on exactly one backend;
    rail/runs/search views are client-side unions. The prototype's "agents" registry is
    this connection list; its Backends page ("ssh tunnel · contract v0.2") is its status.
  - **Remote subagents/applications** = children a session's OWN BACKEND runs through
    clio-relay semantics (P2). The browser never speaks to a relay.
  Verified server support (audit 2026-07-30): contract handshake EXISTS
  (`GET /v1/capabilities` → contract_version + AuthInfo, routes/system.py:435); CORS
  opt-in EXISTS (`gact.cors.origins`, app.py:1219-1233, deny-by-default); auth is the one
  gap — AuthInfo advertises a `schemes` LIST (types.py:149) but only `trust_socket` is
  implemented. Slices: (a) server `bearer` scheme behind the existing advertisement
  (config token, constant-time compare) for non-loopback backends — SSH-forwarded/local
  stay trust_socket; (b) client connection objects + per-connection capabilities check
  with loud refusal on contract mismatch; (c) docs for the CORS knob (web build only).

- **D2 — shared schema home.** TaskRecord/ArtifactRef/ArtifactUse/part shapes must be
  byte-compatible across THREE consumers: clio-agent (python), clio-relay (python,
  `extra="forbid"` strict), gact-tui (TypeScript render types). Two ways:
  - **Option A — shared schema package (RECOMMENDED).** A tiny `clio-schemas` (name TBD)
    package: pydantic models + exported JSON Schema; clio-agent and clio-relay depend on it;
    gact-tui GENERATES its TS types from the exported JSON Schema in CI. Pros: one source of
    truth; the TS-generation kills an entire class of wire drift; growth-friendly (parts,
    provenance, runs will join). Cons: a third release artifact to version; relay pins can
    lag a rev; cross-repo version-bump choreography.
  - **Option B — duplicated models + CI equality tests.** Each repo keeps its own models and
    commits an exported JSON Schema snapshot; each CI diff-tests its snapshot against the
    other repo's committed snapshot; drift = red build. Pros: no new package; relay stays
    fully self-contained (its stated client-agnostic stance). Cons: every schema change is a
    two-repo lockstep dance; gact-tui types still need a generation source; equality tests
    rot if the snapshot-refresh flow is manual.
  **DECIDED 2026-07-30 (owner: "whatever is more correct, regardless of work"): Option A.**
  One canonical schema package; pydantic models + exported JSON Schema; clio-agent and
  clio-relay depend on it; gact-tui generates TS types from the JSON Schema in CI.
- **D3 — Codex as the implementation workhorse** (RESOLVED 2026-07-30; owner motivation is
  TOKEN ECONOMY — far larger Codex allowance with full refreshes — not capability). Primary
  mechanism: the OFFICIAL OpenAI Claude Code plugin **`openai/codex-plugin-cc`** (released
  2026-03-30; owner installed 2026-07-30, active after session restart). It registers
  `/codex:rescue` (delegate a task; `--background/--wait/--resume/--model/--effort`),
  `/codex:review` + `/codex:adversarial-review` (read-only, `--base <ref>`), `/codex:transfer`
  (hand a whole session to a persistent Codex thread), `/codex:status|result|cancel`, and a
  `codex-rescue` subagent; under the hood it brokers a persistent Codex app-server session
  and inherits `codex login` subscription auth.
  Division of labor: **Codex (gpt-5.6 tiers via --model; verify exposed IDs post-install) is
  the DEFAULT implementer** for well-specified slices — dispatched per-slice in git worktrees
  via `/codex:rescue --background`; **Claude/Fable owns orchestration, all merges, the
  hard-taste slices, and review**. ALL reviews are cross-vendor: Codex-authored diffs get
  Claude adversarial review; Claude-authored diffs get `/codex:adversarial-review`.
  Token-economy reality check: every Codex mode (plugin/CLI/exec/SDK) draws ONE shared plan
  meter (rolling ~5h window + weekly cap; parallel workers burn it faster, they don't
  multiply capacity) — so fan-out stays moderate (2-3 background rescues), and the win is
  SHIFTING implementation tokens to the Codex meter, not parallel scale. Budget context at
  Codex's real ~272K cap. Fallbacks if the plugin misbehaves: official Codex SDK
  (@openai/codex-sdk / openai-codex python) or `codex exec --json --output-schema`; NEVER
  Codex native subagents for Sol/Terra (encrypted parent→subagent delegation kills the audit
  trail). Codex-as-MCP-tasks-client remains unconfirmed — nothing depends on it.

### P3 — Interaction + artifact surfaces (server parts + gact-tui renderers)

**Normative input: the mcp_ui_sciences semantic corpus is the UPSTREAM SPECIFICATION for
this phase — not a reference to consult, the baseline to adopt.** The demo's UI was
throwaway; the semantics were the deliverable, produced by deliberate design iteration and
validated against real deployed applications (ParaView, LAMMPS, Darshan, live executions on
clusters via clio-relay). Concretely:

- **P3.0 (first slice of the phase): contract adoption.** Port CONTRACT.md (811 lines,
  authority-over-code) clause-by-clause into the GACT v0.3 SPEC. Every clause is either
  ADOPTED (mapped to its clio-agent/gact-tui counterpart) or DIVERGED with a written reason
  — no silent drops. This covers: the park-reason taxonomy (ask_user_question / elicitation
  / show) unified with our permission-gate stop point; the typed interaction-part vocabulary
  (choice / form / url / show / annotation / free-text direction) and its correlation-id,
  revision-validation, size-limit, stale-state, and replay-identity rules; the three
  provenance-distinct UI pathways sharing one viewport with mandatory teardown transitions;
  private-UI-data slots (browser-only capability data, off the model transcript and SSE);
  A2UI catalog policy (pinned trusted catalogs, progressive disclosure, server-owned action
  routing, bounded direct_mcp routes); image/selection interaction; revision-bound anchors
  and replay-protected reviews; Live Web origin-grant and kill semantics.
- **Ported assets, not rewrites:** the A2UI catalogs themselves (Basic + the CLIO science
  widgets — MRIViewer, DarshanPhaseLens, WorkflowGraph, ParaViewViewer), the sandbox-proxy
  CSP bridge, and the interaction-part schemas. The SEP-2663 evidence bundles
  (evidence/fastmcp-sep2663/, released vs relay v1.5.9) are conformance references for
  P1/P2 as well.
- **The recorded demo sessions are the acceptance corpus** (see gate below): the campaign's
  definition of done for an interaction surface is "the corresponding recorded scenario
  passes on the new stack," which is a far stronger bar than freshly-invented test cases.

- P3.1 MCP Apps renderer (gact-tui): sandbox-proxy + CSP builder pattern, AppBridge JSON-RPC,
  private-UI-data slots (capability data off the model wire), teardown-on-switch. Server path
  already shipped; this is the client half + the app→agent turn loop.
- P3.2 A2UI runtime: pinned local catalogs (Basic + CLIO science widgets), server-owned action
  routing (undeclared → agent turn; declared direct routes bounded), progressive disclosure
  tools for the model.
- P3.3 Live Web artifacts: agent-authored HTML/React artifacts as first-class ui_payload
  artifacts with immutable content-hashed revisions, sandboxed rendering, deny-by-default
  network + user-granted exact origins (rides #974 egress), kill/disable. Design workspace
  (visual editor) explicitly deferred to post-0.10.
- P3.4 SUPPORTED artifacts — the MUST is UI-level artifact INTERACTION, not viewing
  (owner, 2026-07-30). "Supported" means: an agent-created artifact is viewable in the UI
  AND the user can act on its content — highlight a span, get a popup, type a comment, and
  the agent receives a message carrying the anchored context (artifact id + revision +
  quoted span/location + the user's text). Document rendering is the foundation because
  most artifacts are documents.
  - **The annotation primitive (one, shared across kinds):** anchored-context messages.
    Anchor types per kind — text span (markdown, code, logs, answer messages), PDF
    text-layer span, table cell/range (csv/profile views), element ref (html/live-web
    surfaces — the prototype's floating selected-element box is this same primitive),
    region (images/plots, later). Anchors bind artifact + revision + content hash so a
    comment can never silently point at drifted bytes; stale anchors are surfaced, not
    remapped silently. Selection alone stays local; only explicit submission creates the
    agent message (a typed part on the wire — goes in the GACT v0.3 SPEC). The agent's
    response typically lands as a new revision of the same artifact, closing the loop.
  - **Rendering floor (prerequisite):** markdown → trusted DOM; PDF → pinned self-hosted
    viewer with real text layer; sanitized static HTML/SVG (non-executing allowlist);
    office/opendocument (docx/xlsx/pptx/odt/ods/odp) rendered + downloadable as canonical
    bytes. Revisions + provenance identical to every other artifact kind.
  - **Deferred tier (standing open issue, designed-for now):** offline LibreOffice/Docker
    builder, WOPI/OnlyOffice live editing — the issue links the working
    cc_dispatch/mcp_ui_sciences reference code (host/src/host/document_runtime.py ~3000
    LOC, document-runtime/ Docker builder, WOPI plumbing app.py:1162-1477). The artifact
    record + renderer registry + anchor model must accept these without schema change.
  - Gate addition: the P3 scenario includes the full loop live — agent writes a markdown
    report artifact; user highlights a paragraph, comments; agent receives the anchored
    message and revises; the UI shows the new revision with the comment resolved against it.
- P3.5 Interaction cards v2: ask card (multi-select, per-option notes, custom scope, decline),
  permission card states, MCP elicitation rendered through the same cards.
- Gate: the cc_dispatch demo-session library is the scenario source — the repo has BUILT
  sessions demonstrating exactly these surfaces (ParaView mcp-app viewer, LAMMPS runs,
  Darshan mcpui widgets, live executions, A2UI scientific widgets, document artifacts).
  The P3 gate re-runs a curated set of those scenarios against the NEW stack: MCP App
  (ParaView), A2UI (Darshan/science widgets), Live Web report, and each document format,
  with provenance-distinct rendering and teardown proven; visual gate per P5 harness.

## 3b. The gact-tui side is a CONTRACT change, not just new screens (GACT v0.3)

The program cuts a new wire-contract SPEC in gact-tui (the gact-tui#318 pattern: SPEC issue +
locked doc), version-bumped from the current contract. The UI work in P3/P4 consumes these
server-side semantic changes — enumerated here so the client scope is visible:

- **New/extended part kinds on the wire:** run-handle fields on task/tool parts (handle id,
  run label, live states, host); injection parts (background-exit + steering injections);
  a2ui/mcp-app parts (already partly present) with pin/scrub actions; ask parts with
  multi-select options, per-option notes, custom scope, decline; placement/host on task
  parts. All additive; each lands with schema in the SPEC + fixture parity tests.
- **New APIs the UI consumes:** runs registry (list/detach/dismiss, live tickers);
  agents/relays/backends registry CRUD + status (D1 hub); artifact detail payloads for the
  provenance/recreate tabs (lineage route, version record, transform record, reproduce
  bundle — projections of shipped #966 modules); observability projections (timeline/gantt
  rows, session-wide tool aggregation, per-turn artifact attribution, context/cost stats);
  steering/queue APIs (per-child queue CRUD, deliver-now, interrupt, wake); settings-backed
  routes for every settings page that ships visible (unbacked pages ship hidden).
- **Render-contract regeneration:** CANONICAL-CONVERSATION.md and the pre-#880 visual
  fixtures are superseded; P4 locks a CANONICAL-SESSION-V3 contract generated from live
  wire captures of the gate scenarios, and the P5.1 visual harness enforces it.
- **Client deletions:** the old surface set is enumerated and deleted per-slice as v3
  surfaces gate (no dual UI, no legacy render paths kept "just in case").
