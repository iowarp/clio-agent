| FX-F1 | Root cause of the external-call hang. A sync MCP executor chose its event loop when it was built: the bound app's loop, or else a private loop of its own (`SyncMCPToolExecutor.__init__`, `task_calls.application_loop()`). Two callers build or rebuild a workspace fleet with no app bound: task recovery after a restart (`ExternalTasks._recovery_client`) and the commands listing the UI asks for when it opens a conversation (`mcp_prompt_commands.session_executor`). Such a fleet then connects the namespace's proxy session on its private loop (session warm-up's `prepare_namespace`, the prompts listing), and the proxy's backend is one kept-alive stdio session shared by every client of that proxy. A product call runs on the application loop (`AsyncMCPToolExecutor.call_tool_result`, through `ExternalTasks`) and borrows that session: it writes to a session whose reader runs on another loop, which is idle (the request never reaches the server, the reopen stream's "fixture never got the call") or stopped when a superseded fleet is closed (the reply never reaches the caller). The caller waits forever in `_run_foreground_coroutine`, which has no deadline on the application loop by design (#1225) and, outside a turn, no cancellation. ## Decisions

| ID | Decision | Source | Evidence | Status |
| --- | --- | --- | --- | --- |
| FX-D1 | In a GACT server process every sync MCP executor runs on the application loop. `task_call_context.executor_loop()` returns the bound app's loop, or else the server's one serving loop (`loop_guard.server_loops()`, registered by the lifespan). Outside a server (the CLI) the executor still owns a private loop. Built on the serving loop's own thread (blocking there would deadlock the server) or with several serving loops in one process (tests), it keeps a private loop and logs the typed reason `mcp_executor_private_loop` (`built_on_server_loop_thread`, `several_server_loops`). The fix is at the executor, not at the two callers, so a future builder with no app bound cannot bring the hang back | Brief item 1: root cause, no arbitrary timers | `tests/test_tools/test_executor_loop.py` (5 tests; the integration test fails at base and passes here) | passed (live) |
| FX-D2 | A view's call outside a turn is bound to its request (`gact/view_call_cancel.py`): `_run_bound` takes `request=`, and `tools/call`, `resources/read` and the reopen route pass it. The call's cancel event is set when the request disconnects (polled every 0.5 s while the call is in flight: a watch on the requester, not an expiry on the view), when the awaiting task is cancelled, or when CLIO shuts down (`cleanup_all_mcp_apps` calls `cancel_all` first). The session's cancellation checker reads the event, so `_run_foreground_coroutine` cancels the call as a turn's Cancel does. A plain external RPC that no task accepted is then cancelled on the wire (`external_task_connections.abandon_view_call`) and its record says `mcp_app_call_cancelled` (outcome unknown); a turn's call and an accepted task keep their custody rules unchanged. A cancelled reopen answers `call_cancelled`, a new reopen reason, retryable in the UI | Brief item 1: "a call outside a turn must be bound to something cancellable"; plan rule 6 | `tests/test_gact/test_view_call_cancel.py` (7 tests), `test_mcp_app_open.py`; gact-tui `mcp-app-reopen.test.ts` | tests only |
| FX-D3 | A connection replaced while busy (`_retire_superseded`) is kept until its work ends, as before, and is now marked; a call on it that fails records `external_mcp_connection_superseded: <error>` (`external_task_connections.failure_reason`). A replay whose call ended with an uncertain receipt (the connection closed before the service answered) answers `call_failed` with "The connection to the service ended before it answered, so whether it acted on the call is not known." instead of `view_not_opened`. Nothing is retried: the call may have reached the server, and an uncertain mutating call is never replayed | Brief item 1: "fail or retry its pending calls with a typed reason" | `test_external_connection_superseded.py`, `test_mcp_app_open.py::test_every_failure_is_a_typed_reason_with_the_saved_call` | tests only |
| FX-D6 | A view's own call never lands inside a turn that is open (found by q-apps, `sess_221ad09e2e49`: a surface's opening call ran while the agent was answering; its rows split the answer's text inside a code span and were recorded as the agent's call). Each `_run_bound` call runs inside `view_call_transcript.collecting()`, and `tool_observer._append_live_assistant_part(_once)` asks `view_call_transcript.hold()` first (two hook lines; `tool_observer.py` stays at 930). The call's first row decides once where all its rows go: with no turn open, the ordinary no-turn path, unchanged; with a turn open, they are held and written when the call ends as their own assistant message, `metadata.origin: "mcp_app"`, through `_append_session_message`, as an action card outside a turn is. Semantic events already carried no turn id for these calls | Integrator (q-apps) | `tests/test_gact/test_view_call_transcript.py` (the first test fails without the hook: the turn's parts held `tool_call`, `tool_result`); live run FQ4 | passed (live) |
| FX-D7 | `session_work` reads the session's messages and its schedules through `run_off_loop` (`_work_rows`), so a first read after a restart rehydrates the ledger off the loop thread | Integrator (FX-F7; AQ26 and AQ47 need empty `failedRequests` after a restart) | `tests/test_gact/test_session_work_off_loop.py` (fails on the old route: the read ran on the server loop); live FQ6 | passed (live) |
| FX-D8 | Which executor a replay outside a turn uses (integrator's question, q-apps `sess_791744fadd33`, 16:08: a third replay about a minute after two good ones hung in `_run_foreground_coroutine`). `_run_bound` → `_bound_executor` → `ClioAgent._active_tool_executor()`, which returns the workspace's cached executor (`executors[root]`) whoever built it, and builds or rebuilds it when it is missing, reaped or its MCP configuration changed. The builders are: the commands listing (`GET /v1/commands`, a sync route on the thread pool, through `mcp_prompt_commands.session_executor`), the summon targets (sync route), session and workspace warm-ups (worker threads), task recovery (`history.io.run`, the history I/O thread), the reconnect route (`asyncio.to_thread`), and the view call itself (`_run_bound`, a worker thread). None runs on the serving loop's thread, so with FX-D1 every one of them gets the serving loop; the old code gave the four with no app bound a private loop, which is how a replay a minute later could meet a fleet the commands listing had rebuilt on a private loop. A builder on the loop thread would keep a private loop and log `mcp_executor_private_loop reason=built_on_server_loop_thread`; none was logged live, and the agent had 0 private executor loops after restarts, reopens, re-saves and turns (FQ3) | Integrator | code reading of the call sites above; `test_executor_loop.py`; FQ3 | done |
| FX-D4 | `tools.script_media_max` has an operator note in `scripts/config_key_notes.py`; the reference files were regenerated with `scripts/gen_env_reference.py` (`config.defaults.yaml` changed; `docs/ENVIRONMENT.md` and `.env.example` were already current) | Brief item 2 | `tests/test_docs/test_env_reference.py`: 26 passed | done |
