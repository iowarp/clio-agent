# Ledger fragment: `service` stream (MA23, AQ30, AQ31)

Rows use the main ledger's tables. Branch `ws/service` in clio-agent and gact-tui.

## Decisions

| ID | Decision | Source | Evidence | Status |
| --- | --- | --- | --- | --- |
| MA23 | CLIO carries a view's live service. A server declares `_meta["ai.iowarp.clio/service"] = {port, token}` in the result that opens the view. `MCPAppRegistry.register` takes it off the stored result (`split_service_declaration`), so the descriptor, the replayed tool result, the transcript and the model never hold the port or the token. `/v1/sessions/{sid}/mcp-apps/{app_id}/service/{data_ref}/…` proxies HTTP (httpx, already a dependency) and WebSocket upgrades (websockets, already a dependency) to `127.0.0.1:<port>`. Owner modules: `gact/mcp_app_service_declaration.py` (pure parsing, path shape, loopback test), `gact/mcp_app_service.py` (whether to carry it, URL, CSP sources, typed reasons, connection tracking), `gact/mcp_app_service_proxy.py` (routes, preflight middleware). The existing app files get registration and hook lines only. | Plan MA23 | `tests/test_gact/test_mcp_app_service.py` (26 tests); AQ30, AQ31 below | tests only |
| MA23-F1 | Fact: how the app routes' capability is issued and checked. Issued in `MCPAppRegistry.register` (`gact/mcp_apps.py`): `app_instance_id = secrets.token_urlsafe(18)`, `data_ref = secrets.token_urlsafe(32)`, both put on the transcript's `mcp_app` part only (the part carries `app_instance_id` and `data_ref`, nothing private). Checked by `resolve` in `register_mcp_app_routes` (`gact/mcp_app_routes.py`): the session must exist, then `MCPAppRegistry.get(sid, app_id, data_ref)` requires the record to be live (not closed, not expired), owned by `sid`, and `secrets.compare_digest(record.data_ref, data_ref)`; any mismatch is the same non-oracular 404 `not_found`. `get` refreshes the record's idle time. Close is `claim_close` with the same three-way check. The service routes call the same `resolve`. | Plan "What the ledger records" | `gact/mcp_apps.py::MCPAppRegistry.register/get/claim_close`, `gact/mcp_app_routes.py::resolve` read at base `54ae350af` | static |
| MA23-D1 | The capability travels as a path segment, `…/service/{data_ref}/`, not a query parameter or cookie. A page under the route keeps the capability in every relative URL and in a WebSocket built from `location`; a cookie would need `SameSite=None` for a sandboxed `Origin: null` frame and would leak across apps on one origin. `…/service/{data_ref}` redirects to the slash form so relative URLs resolve below it. Services must use relative URLs; a redirect to an absolute path or to the service's own loopback address is rewritten under the route. | Contracts "A view's service" | `test_http_through_the_route_carries_the_token_and_strips_the_browser` | tests only |
| MA23-D2 | The token reaches the service as `Authorization: Bearer <token>` on every proxied HTTP request and WebSocket upgrade. The browser's `Authorization`, `Cookie`, `Origin` and `Referer` are dropped; the service's `Set-Cookie` and `Access-Control-*` are dropped. | MA23 "CLIO adds the token on the way through" | same test (the upstream records the headers it received) | tests only |
| MA23-D3 | "A server CLIO launched" is decided from the session's tool executor: the view's source namespace must have a spec with `transport == "stdio"` in `_clio_namespace_specs` (the gateway's specs for declared servers, `tools/gateway.py::build_gateway`). A URL server is refused with `service_server_not_launched`; the verdict is cached on the record. A port equal to CLIO's own listener is refused with `service_port_is_clio`. A malformed declaration is kept as a refusal (`service_declaration_invalid`), so the descriptor says why. CLIO always dials `127.0.0.1`; there is no host field. | MA23 "only a loopback port, only from a server CLIO launched" | `test_a_server_clio_did_not_launch_gets_no_service`, `test_unreachable_service_and_clio_port_are_typed`, `test_a_malformed_declaration_is_refused_with_a_reason` | tests only |
| MA23-D4 | The service URL is on the sandbox origin (`_sandbox_url`, the same rule as `sandbox_url`), never the UI's origin: framed service pages stay off the workspace origin, and the URL works wherever the sandbox works. The view gets it in the descriptor (`service_url`) and in `hostContext["ai.iowarp.clio/service"] = {url}` on `ui/initialize` and every host-context change; the host checks it is this app's own route on the sandbox origin before passing it. | Contracts | `mcp-app-service.test.ts`; `test_descriptor_gives_the_service_url_and_never_the_token` | tests only |
| MA23-D5 | The sandbox CSP drops every loopback source a resource declares (`127.0.0.0/8`, `localhost`, `*.localhost`, `::1`, `0.0.0.0`) from all directives, and adds only the app's service route (`http(s)://` and `ws(s)://` on the sandbox origin, path-scoped) to `connect-src` and `frame-src`. Each refused source is reported in the descriptor's `csp_refused` and recorded as `csp_loopback_source_refused`. The conformance test that asserted `connect-src 'self' http://127.0.0.1:*` now asserts it is refused. | MA23 "This replaces any rule that lets a view reach 127.0.0.1 directly" | `test_csp_refuses_loopback_and_allows_only_the_service_route`, `test_mcp_v2_conformance.py` sandbox assertion | tests only |
| MA23-D6 | A view's frame is sandboxed without `allow-same-origin`, so its requests carry `Origin: null`. CLIO answers `Access-Control-Allow-Origin: null` on service responses, and an outermost middleware answers CORS preflights for service paths (CLIO's own CORS policy refuses the null origin for its other routes and is unchanged). The token-less origin guard keeps its Host check but skips its state-changing-method check for service paths: the capability in the path is the guard there. | Live need (sandboxed view) | `test_http_through_the_route_carries_the_token_and_strips_the_browser` (null-origin POST, preflight) | tests only |
| MA23-D7 | Closing. `DELETE …/mcp-apps/{app_id}`, session delete and shutdown (`cleanup_session_mcp_apps`) close the app's open WebSockets with code `4410`, reason `mcp_app_closed`, and end in-flight HTTP responses; the route then answers 404. A WebSocket checks the record on each frame, so one whose inline record expired closes at its next frame. No read timeout and no keep-alive ping on an open connection (rule 6); only connecting has a 10 second limit. | MA23 "Closing the app closes the route" | `test_route_is_bound_to_its_own_app_and_closes_with_it` | tests only |
| MA23-D8 | A declaration in a result the view gets through `tools/call` is removed and ignored (`service_declaration_ignored`); only the result that opens the view declares a service. | Rule 5 | `test_a_view_called_tool_cannot_hand_the_view_a_declaration` | tests only |
| MA23-D9 | The service fixture is a Python FastMCP stdio server, `tests/fixtures/mcp_app_service_server.py`, with a hand-written view speaking the MCP Apps messages, not a build of ext-apps `basic-server-vanillajs`: it needs no Node build in the session and keeps the fixture in one file. It starts a token-guarded loopback Starlette service (counter ticking each second over a WebSocket, `GET state`, `POST bump`, a page that opens its own WebSocket), and its view uses only the URL from host context: it opens the WebSocket, fetches state, posts a bump and frames the service page. Port and token can be fixed by `CLIO_SERVICE_FIXTURE_PORT` / `CLIO_SERVICE_FIXTURE_TOKEN` for qualification. | Plan "Fixtures" | the fixture; AQ30 | done |
| MA23-D10 | Typed reasons (`gact/mcp_app_service.py::SERVICE_REASONS`): `service_declaration_invalid`, `service_server_not_launched`, `service_port_is_clio`, `service_not_declared`, `service_unreachable` (502, or WebSocket close 1011), `service_declaration_ignored`, `csp_loopback_source_refused`, `mcp_app_closed`. Each is logged, written to the stream audit and kept in a queryable ring (`recorded_service_reasons`); refusals also reach the descriptor or the HTTP error envelope. | No silent fallback | `test_route_is_bound_to_its_own_app_and_closes_with_it` reads the ring | tests only |
