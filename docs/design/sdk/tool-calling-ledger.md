# Tool calling ledger: exploration, disclosure, `run_code` and the session plan

Rows follow [tool-calling-plan.md](tool-calling-plan.md). Status values are the ones [acceptance-ledger.md](acceptance-ledger.md) defines (`passed (live)`, `tests only`, `static`, `done`, `open`, `blocked`), plus `local phase` for a row the plan assigns to the local qualification pass (open models, a real HA-MCP server, native tool search live, the Tauri desktop, Windows and HPC).

Decisions use the prefix `TD`, evaluation tasks `P` (performance) and `H` (long-horizon), and qualification scenarios `T`.

**What the numbers say.**

- **Wide data work is where current wins, and the reason is model time.** P6 (200 records): base 91 s, current 44 s in every pass. - **P5 (20 records) is level** (16 s against 17 s): current spends one step listing the records before its script, so code pays off from somewhere between 20 and 200 calls, as Anthropic's guidance on programmatic calling predicts.
- **Prompts are smaller.** Cached prompt per step: P1 17k against 27k, P2 23k against 33k, P3 35k against 72k, P8 35k against 44k (the deferred home server). **Correction (2026-11-02):** these figures are the median of cache *reads* per step; a call that wrote its prompt to the cache counted as almost nothing, and base read its prompt from the previous session's cache while current wrote it (finding 17). **What the ablations say.**

- **`run_code` is the feature that pays.** Without it P6 takes 2.5 times as long and 7 times the output tokens, and P7 makes 2,006 direct calls over 34 steps (97k output tokens, 408 s) against 8 calls in 7 scripts. **What the runs show.**

1. **On this model, the export is a short task.** The agent writes one or two analysis scripts (h5py, pandas) that read every run folder and answers in 6 or 7 steps and under 3 minutes. It used no `explore` children and no `run_code`. The OPAL run's 18-25 minutes and about 50 model calls are therefore not explained by the task's width alone. Candidates, not checked from here: the model that run used, the HPC filesystem (1.24 GB), and the clio-core overhead of that time (P7's tool time has since fallen from 303 s to about 60 s). A long-horizon lighthouse for this model needs a task that cannot be scripted in one pass, or the open models of the local phase.
2. **The prompt grows fast on such a task:** 33k cached tokens at the first step, 147k by the sixth, almost all from large shell outputs (the second step prints every document). Context per step, not steps, is what limits run length here.
3. **Compaction never fired at 0.25.** The model's window is 1,000,000 tokens on `claude_code`, so 0.25 is 250k; H5 peaked at 142k and H3 at about 70k, which is why no H3 run in any configuration compacted. H3 and H5 now use 0.05 (`b919ae60`).
4. **After one compaction, auto compaction stopped for the turn.** At 0.05 the run compacted once; the first measurement after it was 58k (system prompt and tools 33k, the summary, the steps kept verbatim) against a 50k threshold, so the guard concluded compaction could not get under it and stopped; the context then grew to 159k. On a 128k open model that is a context overflow after the first compaction. The post-compaction size is now a floor and the next compaction waits for the threshold's share of the room above it (`b919ae60`, `tests/test_gact/test_compaction_no_thrash.py`).
5. **Tool-call blocks the engine could not read.** H5's third step was a `tool_calls` block whose JSON was malformed (the first call's object was not closed before the second began); CLIO answered "could not be read ... send the calls again", and the model changed approach. Across the 1,918 recorded steps in this machine's traces, 45 (2.35%, 34 sessions) were such blocks: 14 not a non-empty list, 13 a missing `,`, 8 several blocks, 3 a missing property quote, 3 XML fragments, 3 a missing opening fence, 1 an unterminated string. Each costs a model step. The cause is that `claude_code` carries tool calls as text, not as native tool use (`lm/engines/text_tools.py`: the transport takes one prompt and no native tools); repairing malformed JSON could execute a guessed command, so it is not repaired. All 14 "not a list" blocks were empty (`[]`), written beside text such as "I'll run these.": the model meant to call tools, so reading an empty block as a final answer would end turns wrongly, and the refusal is right. Open: native tool calls for this engine, which would hand the loop to the CLI (a larger design question).

34. **What a script's tool call costs, and the three changes that cut it (2026-11-05, `47fb4f88`, `e2afbd8e`, `138d36c8`; on `claude/tool-calling-long-horizon` as `c2b6eb3b`, `b8a1b001`, `7862637d`).** The owner asked why a nested call still wrote 7.3 clio-core records after the clio-core work.     | | Store round trips per call | `artifact_index` per call | Median store round trip | Median call interval |
    | --- | --- | --- | --- | --- |

    | Index puts batched (`47fb4f88`) | 7.02 | 1.40 | 5.0 ms | 36.4 ms |

    - **The provenance transform's three index records are sent together.** A writer turn's index puts go as one multi-put before the group flush and its confirms as one after it, keeping the order the pending mark needs (index, event, confirm). A profile with idle stacks showed the call thread waiting half the time while the server sat in `select`: the cost was the interpreter lock being handed between threads. A 0.5 ms switch interval cut the call to 29.9 ms.
    - **The lock was taken by polling.** A pending clio-core write was awaited by sleeping and checking `Future.done()` (0.1 ms doubling to 10 ms): a 4-5 ms put woke up to eight times, each wake retaking the lock. It now blocks in `Future.wait(timeout)`, which iowarp-core 2.4 runs without the lock and bounds by its timeout. The old rule against waiting on an unfinished future came from an earlier binding that blocked forever holding the lock; checked against a private daemon, stopped: returned at 0.50 s, killed: returned `None` at 4.5 s, another thread running throughout. Same gain as the switch interval, without a process-wide setting.

## Agent-facing caps (2026-11-02)

Owner direction: a limit on what the agent may see or do needs a real limit behind it (the model's context window, memory, an OS or provider limit) or must be a default the agent can override per call; a fixed number that decides for the agent is removed (`.claude/CLAUDE.md`, principles 1 to 3).
