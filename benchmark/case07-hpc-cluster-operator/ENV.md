# case07 isolated-instance environment

The GOAL.md "Isolation (parallel-clio)" contract for this case's live serve,
made concrete. This document is the reference; `bring_up_isolated_serve.sh` is
the script that actually exports it. Neither ever touches the ares-mission
serve on `:17900` (`D:/Libraries/Documents/projects/clio-agent`, the main
tree) or any relay worktree -- this worktree (`D:/clio-cluster-case`) and its
own isolated serve process are the only things either file starts or stops.

## Port

- `CLIO_GACT_FIXTURE_PORT=17970` -- read by
  `tests/test_real_cases/conftest.py`'s `gact_server` fixture (default
  `17960`, shared with earthscope/wildfire). Setting this env var before
  `pytest` retargets that SAME fixture at `:17970` with zero new fixture code
  -- the live-test recipe below is the only thing that needs to change.
- `bring_up_isolated_serve.sh` launches its own standalone serve on the same
  port for manual/interactive poking (relay wiring smoke checks) independent
  of a pytest run; it is not required for `pytest` runs, which manage their
  own server lifecycle via the fixture.

## Data / artifacts / file-tool access

There is no single `CLIO_DATA_DIR` knob in this codebase (`src/clio_agent/paths.py`
is the source of truth: `CLIO_USER_DIR` overrides the per-user config/cache/data
root; there is no separate "data dir" variable). This case deliberately does
**not** set `CLIO_USER_DIR`:

- GOAL priority 1 is "install workspace-scoped in the isolated instance" -- the
  `cluster-operator` pack is installed scoped to the run's OWN workspace, not
  the shared user blueprint registry, so the isolated instance can share the
  same user-level config (provider auth, other installed packs) as the
  ares-mission serve on `:17900` without a scoped registry collision.
- `tests/test_real_cases/conftest.py`'s `gact_server` fixture already strips
  `XDG_CONFIG_HOME` from the env it hands the server (so a live grind sees the
  REAL installed-blueprint registry, not a throwaway one) -- overriding
  `CLIO_USER_DIR` here would fight that existing, deliberate behavior.

What IS isolated, and how:

- **Session/workspace data**: `agent.run({..., "workdir": ...})` roots each
  scenario's session workspace (`.clio/agent`, `.clio/core`) under
  `D:/clio-cluster-case/benchmark/case07-hpc-cluster-operator/runs/workspace/<scenario>`
  (see `test_case07_cluster_operator.py`'s `workspace_root`, overridable with
  `CLIO_CASE07_WORKSPACE_ROOT`) -- durable, worktree-local, never a pytest
  `tmp_path` that gets wiped, never the repo root.
- **File-tool access**: `CLIO_ALLOWED_ROOTS` must include the worktree so the
  agent's fs tools (and the workspace `.clio` dir) resolve inside it:

  ```
  export CLIO_ALLOWED_ROOTS='D:\clio-cluster-case;C:\Users\jaime;/tmp'
  ```

  (The conftest default is `f"{Path.home()}:/tmp"` -- home already covers most
  cases since the workspace lives under the worktree drive, but set this
  explicitly for the isolated bring-up so the contract is not implicit.)

## Relay door + owned session identity

Mirrors `D:/relay-p5local/serve-ares-env.sh` (the ares-mission `:17900`
recipe) with the port changed and the session identity SOURCED live instead of
hardcoded, since GOAL.md requires "a fresh owned-session identity (documented
in runs/ENV.md when minted)" and the p5local session is re-minted periodically
(`D:/relay-p5local/session.env`, regenerated by `session start`):

```bash
export CLIO_RELAY_MCP_URL='http://127.0.0.1:18795/mcp'   # the p5local door (already running on :18795 -- see door.sh; this case does NOT start it)
export CLIO_RELAY_CLUSTER="${CLIO_RELAY_OWNER_SESSION_CLUSTER:-ares-p5run2}"
export CLIO_RELAY_API_TOKEN="$(cat /d/relay-p5local/api-token.txt)"
. /d/relay-p5local/session.env   # sets CLIO_RELAY_OWNER_SESSION_ID / _SESSION_GENERATION_ID / _OWNER_SESSION_CLUSTER / _OWNER_SESSION_API_PORT
export CLIO_RELAY_HTTP_URL="http://127.0.0.1:${CLIO_RELAY_OWNER_SESSION_API_PORT:-8796}"
```

The p5local door itself (`:18795`) is SHARED infrastructure (one door serves
one `CLIO_RELAY_INPUT_WORKSPACE_ROOT`, per `env.sh`'s comment) -- this case
does not start or stop it; `bring_up_isolated_serve.sh` only verifies it is
reachable before starting the isolated serve. The ares cluster itself is also
shared, real infra (GOAL: "concurrent use is fine; mind capacity").

## Provider / guardrail cell

```bash
export CLIO_LM_PROVIDER='claude_code'
export CLIO_LM_MODEL='sonnet'
```

`tests/test_real_cases/clio_sut.py`'s `bind()` sets these per-cell over HTTP
(`PUT /v1/providers/lm`) for a `pytest` run regardless of the ambient env; the
env vars above only matter for `bring_up_isolated_serve.sh`'s standalone,
non-pytest launch (mirroring `serve-ares-env.sh`'s pattern).

## Recipes

Prepare env + start the isolated serve directly (manual poking, relay-wiring
smoke checks, NOT required for `pytest`):

```bash
. D:/clio-cluster-case/benchmark/case07-hpc-cluster-operator/bring_up_isolated_serve.sh
```

Run the live S1 acceptance cell through `pytest` (the fixture manages its own
server lifecycle; only the port needs pointing):

```bash
cd /d/clio-cluster-case
. /d/relay-p5local/env.sh   # relay door/session identity onto the ambient env
export CLIO_RELAY_MCP_URL='http://127.0.0.1:18795/mcp'
export CLIO_RELAY_HTTP_URL="http://127.0.0.1:${CLIO_RELAY_OWNER_SESSION_API_PORT:-8796}"
export CLIO_RELAY_CLUSTER="${CLIO_RELAY_OWNER_SESSION_CLUSTER:-ares-p5run2}"
export CLIO_GACT_FIXTURE_PORT=17970
CLIO_RUN_LIVE=1 uv run pytest \
    tests/test_real_cases/test_case07_cluster_operator.py \
    -k s1_capability --provider claude_code --model sonnet \
    -o addopts="" -p no:cacheprovider -q
```
